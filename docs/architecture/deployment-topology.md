The Vendure Admin API/Dashboard must be protected more strongly than the public Shop API and must not share the same public edge policy unnecessarily.

## Local development topology (concrete, established `FOUND-018`)

```text
apps/server  --dev:server--> Vendure Server  :3000  (Admin/Shop API, Dashboard, GraphiQL, dev mailbox)
apps/server  --dev:worker--> Vendure Worker         (job queue, search indexing, scheduler)
apps/server  --dev:dashboard--> Dashboard build     (Vite dev server; the running Server also serves
                                                      it at :3000/dashboard, per ADR-0013)
apps/storefront --dev--> Next.js Storefront  :3001

apps/server/docker-compose.yml --up -d postgres_db--> PostgreSQL 16  :6543  (host) -> 5432 (container)
```

`npm run dev` in `apps/server` (`vendure dev all`) runs the server, worker, and Dashboard together, as generated. `npm run dev:server`/`dev:worker`/`dev:dashboard` run them individually when isolating a boot issue.

**Deviation from this document's original wording:** the plan originally called for a compose file under `infra/compose/`. Once `apps/server/docker-compose.yml` was actually inspected (generated by `@vendure/create`, committed in `FOUND-014`), it already defines `postgres_db` (the one currently used), plus `mysql_db`, `mariadb_db`, `redis`, `typesense`, and `elasticsearch` services with sensible defaults and non-colliding host ports — i.e. it already **is** the "production-equivalent local topology" compose file this section originally asked `infra/compose/` to provide, colocated with the app that needs it (consistent with `ADR-0013`'s "don't fight the generated scaffold" principle). Duplicating it into `infra/compose/` would create two compose files that could drift out of sync. **`infra/compose/` is reserved for genuinely cross-app orchestration** (e.g. a future single command bringing up server + worker + storefront + Postgres together) or production deployment manifests, not a redundant copy of `apps/server`'s own dev infra. `infra/docker/`, `infra/compose/` remain empty until such a cross-app need materializes.

## Health checks (`FOUND-018`)

| Component                  | Check                                                                        | Design rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/server`              | `GET /health` → `{"status":"ok"}`                                            | Built into `@vendure/core`, generated as-is. **Vendure's own source marks this feature deprecated as of the version bootstrapped here** ("Application-level health checks are an anti-pattern — health monitoring should be handled by your infrastructure, e.g. Kubernetes probes, Docker healthchecks, load balancer checks"). Kept as a plain liveness signal only; deliberately **not** extended with in-app DB/queue-aware logic that the framework itself is moving away from.                                            |
| `apps/storefront`          | `GET /api/health` → `{"status":"ok","service":"storefront","timestamp":...}` | New (`src/platform/health/handler.ts`, re-exported from `src/app/api/health/route.ts`, following the codebase's existing `platform/` + thin `route.ts` re-export convention used by `/api/revalidate`). Deliberately does **not** round-trip to the Vendure Shop API — coupling storefront liveness to backend reachability would turn a transient backend blip into a storefront outage, the wrong failure mode for a customer-facing edge process. `Cache-Control: no-store` so a monitor never sees a stale cached response. |
| PostgreSQL (`postgres_db`) | Docker Compose `healthcheck:` (`pg_isready`, 5s interval, 10 retries)        | Infra-level DB readiness, per Vendure's own current guidance above — verified: `docker compose up -d postgres_db` reports the container `(healthy)` after recreation. This is the pattern to extend (not duplicate in-app) for Redis/OpenSearch health once those land (Phase 11/Phase 8).                                                                                                                                                                                                                                      |

Composing backend readiness (DB up + migrations applied + server accepting connections) is therefore an **infrastructure-layer** concern — e.g. a startup/deploy script that waits for `postgres_db`'s Docker healthcheck before starting the server, and the server's own `runMigrations()` (see `migrations.md`) failing loudly if migrations can't apply — rather than a single elaborate `/health` endpoint trying to report on everything at once.

## Asset pipeline (`FOUND-021`)

`AssetServerPlugin` was already configured by the `FOUND-014` scaffold (`apps/server/src/vendure-config.ts`) — local dev uploads go to `apps/server/static/assets` on local disk, served at `/assets`. No code change was needed for this task; it consisted of verifying the pipeline end to end and defining the production storage boundary.

**Verified (this task's required upload/read integration test):** authenticated as `superadmin` via the Admin API, uploaded a real JPEG through `createAssets` (GraphQL multipart request spec), received back a `preview`/`source` URL pair, then fetched the `preview` URL directly and confirmed the response is a valid JPEG (`ffd8ff...` magic bytes, correct byte count for the resized preview variant). Full round trip works.

**Finding, documented not fixed (outside this repo's control):** the URLs `createAssets` returned on this Windows dev machine contain literal backslashes as path separators (e.g. `.../assets/preview\f1\name.jpg` instead of `.../assets/preview/f1/name.jpg`) — `@vendure/asset-server-plugin` appears to build the URL with an OS-native `path.join` rather than a URL-safe join. It happened not to break this test (both the backslash and forward-slash forms returned `200`, likely because Node/Express's static-file resolution normalizes separators on Windows at the filesystem layer) — but a literal backslash is not a URL path separator on Linux, where production will run, and a browser may not resolve it the same forgiving way. **Action:** re-verify this specific behavior once local dev or CI runs on Linux (Phase 11 hosting work, or earlier if a Linux CI runner is used in `FOUND-023`); do not assume the Windows-observed "it still works" result generalizes. Not something to patch in a vendored, compiled dependency at this stage.

**S3-compatible interface boundary (pending `ADR-0003`):** `AssetServerPlugin`'s local-disk storage strategy is a dev-time convenience the plugin itself supports switching away from via its `storageStrategyFactory` option, without any change to the rest of the application — Vendure's asset storage is already an abstracted interface, not something LIPEK needs to build a boundary around. The production cutover (`OPS-008`, Phase 11) is: once `ADR-0003` selects a provider (Cloudflare R2 or Backblaze B2, per that ADR's provisional recommendation), swap `storageStrategyFactory` to an S3-compatible implementation and point `assetUrlPrefix` at the real CDN/bucket URL — no application code outside `vendure-config.ts` needs to change, since nothing else in the codebase constructs asset URLs itself (both apps only ever consume the `source`/`preview` URLs Vendure's own API already returns).
