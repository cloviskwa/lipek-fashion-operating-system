## 2. Responsibility Matrix

For each top-level unit: what belongs there, what must never belong there, and what it depends on.

### `apps/server`
- **Responsibility:** system of record for commerce, content, services, CRM, documents. Owns PostgreSQL schema and all migrations. Hosts the Vendure Admin API, Shop API, and the Vendure Dashboard (via `@vendure/dashboard` mounted/served by this app).
- **Belongs here:** Vendure plugins, GraphQL API extensions, domain entities, event listeners, background jobs, payment/email/SMS provider adapters, MFA/social-auth strategies, RBAC/permission definitions, audit logging.
- **Must not belong here:** any customer-facing rendering/UI, direct calls out to the AI service's model provider (the AI service calls *into* `apps/server`'s APIs, never the reverse for model inference), hard-coded business content that staff should edit.
- **Depends on:** PostgreSQL, Redis/BullMQ (production), object storage. Is depended on by `apps/storefront`, `apps/mobile/*`, `apps/ai` (as a tool-calling target), `apps/staff-console-extensions` (build-time bundling target).

### `apps/storefront`
- **Responsibility:** customer experience rendering layer (SOT §3.1 "renderer, not system of record"). SSR/RSC via Next.js App Router, PWA shell, AEO surface (`llms.txt`, structured content), dark/light theme UI, AI chat UI (calling a BFF route into `apps/ai`).
- **Belongs here:** presentation components, route composition, client-side interaction, Shop API queries (server-side preferred), session/cookie handling for customer auth (including OAuth redirect handling for Google/Apple and MFA challenge UI).
- **Must not belong here:** Admin API credentials, business rule logic that should live in Vendure plugins, hard-coded catalog/navigation/promotions data.
- **Depends on:** `apps/server` Shop API, `packages/ui`, `packages/graphql`, `apps/ai` (AI BFF route only).

### `apps/staff-console-extensions`
- **Responsibility:** source location for LIPEK's Vendure Dashboard extensions (custom routes, widgets, forms, tables) for Tailoring, Alterations, Laundry, CRM, Content, Documents, Loyalty, AI Escalations, Analytics/Operations, and the MFA/security administration screens. Kept as a distinct app (rather than inline under `apps/server`) purely for independent linting/testing/review of dashboard-extension code; it is still built and served as part of the Dashboard bundle.
- **Belongs here:** React (Dashboard SDK) components/pages, dashboard navigation registration, Dashboard-side forms and widgets.
- **Must not belong here:** business logic/validation that should live server-side in `apps/server` plugins (the Dashboard extension calls the Admin API; it does not reimplement domain rules).
- **Depends on:** `apps/server` Admin API/GraphQL schema, `packages/ui`, `packages/graphql`.

### `apps/mobile`
- **Responsibility:** app-ready packaging of the platform for three distinct audiences — **customer**, **delivery/courier**, and **staff/admin** — satisfying the "app-ready (Android, iOS)" requirement. Each sub-app is a thin native/hybrid shell around the same backend contracts; no duplicate business logic.
- **Belongs here:** native shell configuration (Capacitor or chosen alternative per ADR-0007), push-notification wiring, device-specific UX (camera for garment/alteration photo upload, geolocation for delivery), app-store metadata.
- **Must not belong here:** a second copy of storefront or dashboard business logic — mobile apps consume the same GraphQL APIs as `apps/storefront`/`apps/staff-console-extensions`, ideally wrapping shared `packages/ui` components where the framework choice allows.
- **Depends on:** `apps/server` (Shop/Admin API), `packages/ui`, `packages/graphql`.

### `apps/ai`
- **Responsibility:** Mastra-based agent orchestration (SOT §23A). Owns agent definitions, tools, RAG ingestion/retrieval, memory, evals.
- **Belongs here:** agent/tool/workflow code, RAG ingestion pipelines, eval datasets/scorers.
- **Must not belong here:** direct database access outside its own logically-isolated pgvector schema; unrestricted HTTP fetch tools; any customer data store not scoped by authorization.
- **Depends on:** PostgreSQL + pgvector, authorized tool endpoints exposed by `apps/server` (never raw SQL), `apps/storefront`'s AI BFF route as its inbound entry point.

### `packages/ui`
- **Responsibility:** shared, framework-agnostic-where-possible design system: tokens (including the dark/light theme token pairs), primitives (`Container`, `Section`, `Cta`, `Card`, `Badge` — migrated from the current prototype), and composed patterns reused across storefront, dashboard extensions, and mobile where feasible.
- **Must not belong here:** business/domain logic, API calls, anything specific to one app's routing.
- **Depends on:** nothing internal; everything else may depend on it.

### `packages/schemas`
- **Responsibility:** shared Zod (or equivalent) contracts for cross-app payloads — form validation, MFA enrollment/challenge payloads, webhook payloads, AI tool input/output shapes.
- **Depends on:** nothing internal.

### `packages/graphql`
- **Responsibility:** generated types/documents from the Vendure Shop and Admin schemas (codegen output), consumed by storefront, dashboard extensions, and mobile.
- **Must not belong here:** hand-written business logic — this package is generated/derived and must be regenerable from `apps/server`'s schema.

### `packages/config`
- **Responsibility:** shared ESLint/TypeScript/build configuration so every app enforces the same standards (including strict TS, accessibility lint rules).

### `packages/testing`
- **Responsibility:** shared fixtures, factories, and test helpers (e.g. seeded customer/order fixtures, MFA test harness, mock payment webhook payloads) used by unit/integration/E2E suites across apps.

### `docs/`
- **Responsibility:** all documentation defined in SOT §0D plus this engagement's deliverables. Each document states whether it is authoritative, derived, provisional, or operational (see [`DOCUMENTATION_MAP.md`](../implementation/DOCUMENTATION_MAP.md)).
- **Must not belong here:** the source of truth's *internal-only* variant must never be duplicated into any `public/`-servable path of any app.

### `infra/`
- **Responsibility:** Docker Compose definitions for local Postgres/Redis/OpenSearch/asset-storage-emulator, and deployment manifests/IaC once the hosting ADR is resolved.
- **Must not belong here:** production secrets (use the environment-variable contract in `docs/implementation/environment-variables.md` and a secrets manager, never committed files).

### `scripts/`
- **Responsibility:** repo-level automation (bootstrap, codegen trigger, seed data loader, dependency-register lint, migration helpers).

### Root: `AGENTS.md`, `CLAUDE.md`, `pnpm-workspace.yaml`, `package.json`, `pnpm-lock.yaml`
- **Responsibility:** monorepo entry points and coding-agent operating contracts. `AGENTS.md`/`CLAUDE.md` restate the bootstrap sequence (SOT §0E) and the "Do Not" list (SOT §52E) so every future agent session starts aligned without re-reading the full SOT line-by-line (though the SOT remains the precedence authority per SOT §0.1).

## 3. Cross-Cutting Concern Placement

The four requirements this engagement explicitly added beyond the SOT's own text are placed as follows — none of them get a bespoke top-level folder; they are cross-cutting and live inside the structure above:

| Concern | Where it lives | Why |
|---|---|---|
| **MFA + social login (Google/Apple/email) + security hardening** | `apps/server/src/plugins/lipek-security/` (server-side strategies, TOTP/WebAuthn, RBAC, audit log) + `apps/storefront` auth UI/redirect handling + `apps/staff-console-extensions` for admin-side MFA enforcement screens | Auth is a Vendure `AuthenticationStrategy` concern (server-authoritative); no app may implement its own parallel identity store (SOT §52B "no shadow copies of core customer data"). |
| **App-readiness (Android/iOS) for customers, delivery, admin** | `apps/mobile/{customer,delivery,staff}` | Kept separate from `apps/storefront` because each audience has a different auth scope, permission set, and release cadence, while still consuming the same backend contracts. |
| **Dark/light theme** | Tokens in `packages/ui`, provider/toggle logic in each consuming app (`apps/storefront/lib/theme`, dashboard extension theming hooks, mobile theme bridge) | Theming is a design-system concern (single source of tokens) with per-app runtime wiring (each renderer applies tokens differently: CSS custom properties on web, native theming on mobile). |
| **SEO + AEO** | `apps/storefront/lib/seo` (metadata, JSON-LD, `llms.txt`, structured Q&A/knowledge routes) sourced from `LipekContentPlugin` and catalog data in `apps/server` | AEO is a storefront rendering concern over backend-owned content, exactly like traditional SEO — no separate service needed. |

## 4. Dependency Direction Rules

1. `apps/*` may depend on `packages/*`. `packages/*` must never depend on `apps/*`.
2. `apps/storefront`, `apps/staff-console-extensions`, and `apps/mobile/*` depend on `apps/server`'s published API contracts (GraphQL schema/`packages/graphql`), never on its internal modules or database directly.
3. `apps/ai` depends on `apps/server`'s authorized tool endpoints, never on the database directly (SOT §31, §52C).
4. No app may write to another app's data without going through its owning API (SOT §52B "no service is allowed to silently create shadow copies").
5. `docs/` and `infra/` are read by humans/CI/deployment tooling, not imported by application code.

---

## 5. What Must Not Be Reproduced From the Prototype

Per the Gap Analysis `CONFLICT` items, the target structure explicitly does **not** carry forward:
- Any static JSON content tree functioning as the production data source (`src/content/*` becomes seed/fixture data only, moved under `packages/testing` fixtures or a documented seed script in `scripts/`, not a runtime dependency of `apps/storefront`).
- Hard-coded navigation/category/tag arrays in application source (`src/lib/config/site.ts`'s `NAV_LINKS`/`FOOTER_LINK_GROUPS` pattern is replaced by `NavigationMenu`/`NavigationItem` entities served from `apps/server`).
- The source of truth document living inside any `public/`-servable directory of any app.

## 6. Migration Plan: Current → Target

This sequence is designed to be **safe and incremental** — nothing here executes yet; it is the plan Phase 1 (`FOUND-013`–`FOUND-020`) follows.

```text
STEP 1 — Commit the current uncommitted state as-is
   Stage and commit the pending deletions (old scaffold) and the new Next.js
   app exactly as they exist today, so there is a clean, reviewable baseline
   before any restructuring. Do not mix this commit with new work.
        ↓
STEP 2 — Quarantine the source-of-truth document
   Move `public/docs/LIPEK_MASTER_TECHNICAL_SOURCE_OF_TRUTH.md` (and the stray
   `.docx`/`~$...docx` files) out of any `public/`-servable path — e.g. into
   `docs/internal/` at repo root — before any further work, independent of
   the rest of the migration. This is a P0 exposure fix, not scheduled work.
        ↓
STEP 3 — Scaffold the monorepo shell
   Create `pnpm-workspace.yaml` packages globs, `apps/`, `packages/`, `infra/`,
   `scripts/`, `docs/` (already begun by this engagement), `AGENTS.md`,
   `CLAUDE.md` at repo root. No app code moves yet.
        ↓
STEP 4 — Bootstrap apps/server and apps/storefront from the official Vendure scaffold
   Run `@vendure/create` into `apps/`, selecting PostgreSQL and the official
   Next.js storefront starter, per SOT §0F.1. This produces a *new*
   `apps/storefront`, deliberately not a copy of the current root-level app.
        ↓
STEP 5 — Port reusable presentation assets into the new apps/storefront
   Migrate (not copy verbatim): design tokens → packages/ui, route/IA
   structure → apps/storefront routes (now reading from Vendure/CMS APIs
   instead of local JSON), SEO/JSON-LD builder pattern → apps/storefront/lib/seo,
   UI primitives → packages/ui, current src/content/*.json → seed fixtures.
        ↓
STEP 6 — Retire the root-level prototype app
   Once apps/storefront reaches parity on the migrated routes, remove the
   root-level src/app, src/components, src/content, src/lib, src/styles
   (they no longer serve any purpose once superseded — this is a deliberate,
   reviewed deletion, not an accidental one).
        ↓
STEP 7 — Resolve the mobile-wrapper decision (ADR-0007)
   Either move mobile-wrapper/ into apps/mobile/customer as the starting
   point, or replace it entirely, based on the ADR outcome. Do not leave it
   disconnected at repo root.
        ↓
STEP 8 — Re-introduce hosting config once the hosting ADR (ADR-0009) lands
   Only then decide whether any trimmed netlify.toml/vercel.json equivalent
   is reintroduced for the storefront's static/edge assets, alongside
   whatever hosts apps/server + apps/ai.
```

Each step above corresponds to a task ID in [`MASTER_IMPLEMENTATION_PLAN.md`](../implementation/MASTER_IMPLEMENTATION_PLAN.md) Phase 0/1 (`FOUND-004`, `FOUND-013`–`FOUND-020`).
